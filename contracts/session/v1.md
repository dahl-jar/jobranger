# Session v1

Byte layout of the end-to-end session between the CLI and a browser. The relay forwards envelopes (`contracts/envelope.schema.json`) and sees `v`, `channel`, `sid`, `seq`, `kind` and `ciphertext`. `data` ciphertext is AES-GCM output. `hello` steps are readable base64url JSON: the relay sees every step field, including the public keys, `commit`, `nonce_b`, `agent` (the browser name, visible to the relay by design) and the MACs.

## Notation

- `||` is concatenation. Quoted strings in byte expressions are their ASCII bytes.
- `u16be(x)` and `u64be(x)` are unsigned big-endian integers of 2 and 8 bytes.
- `LABEL` is `"jobranger v1"`.
- `pub(k)` is the 32-byte raw X25519 public key of `k`.
- Hashes, MACs, HKDF and AAD take raw bytes. JSON fields and envelope fields carry binary values as base64url (RFC 4648 section 5).

Base64url values are canonical: only `A-Z`, `a-z`, `0-9`, `-` and `_`, no padding, no whitespace, and the value re-encodes to the same string. Anything else is rejected. `contracts/envelope.schema.json` uses the same alphabet.

Sizes: public keys 32 bytes, `sid` 16, `nonce_b` 16, `commit` 32, `mac` 32, `pair_tag` 16.

`CHUNK_THRESHOLD_BYTES`, `CIPHERTEXT_B64_MAX_CHARS`, `GCM_TAG_BYTES`, `HELLO_MAX_BYTES`, `AGENT_MAX_BYTES`, `AGENT_DISPLAY_MAX_CHARS`, `STEP_TIMEOUT_SECONDS`, `PAIR_CONFIRM_TIMEOUT_SECONDS` and `COMMAND_DEDUPE_SECONDS` live in the contract limits files, `cli-python/src/jobranger/contract/limits.py`, `web/src/features/relay/contract/limits.ts` and `contracts/src/Jobranger.Contracts/Limits/ContractLimits.cs`, which spells each name in PascalCase (`ChunkThresholdBytes`).

## Keys

- `cS`: CLI static X25519 key, kept across sessions.
- `cE`: CLI ephemeral X25519 key, new for every handshake.
- `bS`: browser static X25519 key, kept in the browser across sessions.
- `bE`: browser ephemeral X25519 key, new for every handshake.

The browser holds X25519 keys only. The CLI also has an Ed25519 key that signs relay requests and names the channel:

```text
channel = base64url(SHA-256("jobranger-chan" || CLI Ed25519 public key))
```

## Envelope use

- `kind: "hello"`: `seq` is 0. `ciphertext` is base64url of the UTF-8 JSON of one handshake step, at most `HELLO_MAX_BYTES` (4,096) bytes of JSON.
- `kind: "data"`: `seq` is 1 or more. `ciphertext` is base64url of the AES-GCM output in [Data frames](#data-frames).
- `sid` is base64url of the session id. The browser picks a new one for each handshake. Browser-to-CLI frames carry the sender's `sid`, CLI-to-browser frames the target's.

One CLI connection serves a channel at a time. Every rule assumes a single CLI peer.

The relay binds each `sid` to the browser connection that sent the first frame with it, until that connection closes or the channel's CLI connection closes or is replaced, and drops browser frames with that `sid` from any other connection. The relay calls the CLI hub method `SessionsClosed` with `{"sids": ["..."]}` when a browser connection closes. `sids` lists the `sid`s that connection held, and the CLI drops their state. The notice sits outside the envelope and only closes sessions.

## Handshake

Every step is a JSON object with `t`, the step name. The envelope carries the `sid`.

1. Browser sends `commit`:

   ```json
   {"t": "commit", "browser_static": "<pub(bS)>", "commit": "...", "pair_tag": "..."}
   ```

   `sid` and `nonce_b` are random bytes. `agent` is the UTF-8 bytes of the browser name sent in `reveal`.

   `pair_tag` binds a pairing commit to the code the browser claimed. The browser sends it only while pairing, when it has no stored `cli_static`. A paired handshake omits the field. `code` is the claimed code as the terminal shows it (`XXXX-XXXX`, upper case), in UTF-8. `PAIR_TAG_LABEL` (`"jobranger pair v1"`) and `PAIR_TAG_BYTES` (16) live in the contract limits files.

   ```text
   pair_tag = HMAC-SHA256(key = code, PAIR_TAG_LABEL || channel)[0:PAIR_TAG_BYTES]
   ```

   `channel` is the 32 raw bytes of the channel id. While pairing runs, the CLI accepts a `commit` with an unpaired `browser_static` only when its `pair_tag` matches the tag of the CLI's current code, compared in constant time. It ignores any other such `commit` without an answer, as it ignores a foreign `sid`.

   ```text
   commit = SHA-256("jobranger v1 commit" || pub(bS) || pub(bE) || nonce_b
                    || u16be(len(agent)) || agent)
   ```

2. CLI sends `offer`:

   ```json
   {"t": "offer", "cli_static": "<pub(cS)>", "cli_eph": "<pub(cE)>"}
   ```

   Outside pairing the browser runs a handshake only with a stored `cli_static`, and aborts when the `offer`'s `cli_static` differs.

3. Browser sends `reveal`:

   ```json
   {"t": "reveal", "browser_eph": "<pub(bE)>", "nonce_b": "...", "agent": "Firefox on macOS"}
   ```

   `agent` is the browser name shown in the terminal, a JSON string of at most `AGENT_MAX_BYTES` (256) bytes in UTF-8. A longer string, a lone surrogate or invalid UTF-8 aborts the handshake. `agent` is untrusted display text. Before any terminal output the CLI keeps only characters from `[A-Za-z0-9 ._()/-]`, cuts the result to `AGENT_DISPLAY_MAX_CHARS` (48) characters, and shows `a browser` when nothing is left.

   The CLI uses the `browser_static` from `commit` as `pub(bS)` for `commit` and `th`. It recomputes `commit` and aborts on a mismatch. The browser fixes every value it adds to `th` in `commit` before it sees the CLI's keys, so a relay in the middle cannot search for values that give matching words.

4. CLI sends `confirm`:

   ```json
   {"t": "confirm", "mac": "..."}
   ```

   ```text
   mac = HMAC-SHA256(key_confirm, "cli" || th)
   ```

   The browser verifies `mac` and aborts on a mismatch.

5. Browser sends `confirm` with the same shape:

   ```text
   mac = HMAC-SHA256(key_confirm, "browser" || th)
   ```

   The CLI verifies `mac` with a constant-time compare and aborts on a mismatch.

Each side sends data only after it has sent its own `confirm` and verified the peer's. [Pairing](#pairing) adds conditions during pairing.

Each handshake step must arrive within 15 seconds of the previous step (`STEP_TIMEOUT_SECONDS`).

When `browser_static` in `commit` is not a paired device and no pairing is running, the CLI answers that `commit` with `{"t": "unknown_device"}` and keeps no state for the `sid`. The step is unauthenticated. The browser keeps any stored `cli_static`, and offers to pair again only when the user asks.

## Key schedule

Both sides compute these after `reveal`. `th` is the transcript hash, `transcript_hash` in the test vector.

```text
th  = SHA-256(LABEL || sid || pub(cS) || pub(bS) || pub(cE) || pub(bE)
              || nonce_b || u16be(len(agent)) || agent)

ikm = X25519(cE, bE) || X25519(cS, bE) || X25519(cE, bS)    CLI
ikm = X25519(bE, cE) || X25519(bE, cS) || X25519(bS, cE)    browser

okm = HKDF-SHA256(ikm, salt = th, info = "jobranger v1 keys", L = 96)
key_c2b     = okm[0:32]
key_b2c     = okm[32:64]
key_confirm = okm[64:96]

sas = HKDF-SHA256(ikm, salt = th, info = "jobranger v1 sas", L = 8)
```

`ikm` is 96 bytes. An all-zero X25519 output aborts the handshake (`ValueError` from Python `cryptography`, `OperationError` from WebCrypto `deriveBits`).

## Confirmation words

`W` is the EFF short wordlist 2 in list order, 1296 words, one per line in `contracts/crypto/eff_short_wordlist_2.txt`.

```text
n = sas read as an unsigned 64-bit big-endian integer
repeat 4 times:
    next word = W[n mod 1296]
    n = floor(n / 1296)
```

The four words carry about 41 bits. During pairing the terminal and the website show the words in that order.

## Pairing

A browser stores `cli_static` only through a pairing handshake: words shown, website Yes, and the first CLI data frame verified. Until then every handshake it runs is a pairing handshake. If the browser's relay connection drops, or the page reloads, before the first CLI data frame verifies, the browser discards the pending pairing (channel, ticket and keys). The user pairs again, and the browser makes a new static key `bS` for that pairing.

The user confirms the match on both sides. The browser sends its `confirm` only after the user confirms on the website. A rejection on the website aborts the handshake.

During pairing the terminal shows the words when the CLI sends its `confirm`. The user may answer in the terminal before or after the browser's `confirm` arrives. The CLI's handshake for the candidate ends when it has both the terminal answer and the browser's verified `confirm`. The CLI sends data only after that. A browser data frame on the candidate `sid` that arrives earlier breaks the rules. The browser sends data only after the first CLI data frame verifies. A rejection in the terminal leaves nothing stored.

The browser's `confirm` and the terminal answer each wait up to 120 seconds (`PAIR_CONFIRM_TIMEOUT_SECONDS`) in place of `STEP_TIMEOUT_SECONDS`. Each side's timer starts when that side shows the words. The browser's wait for the first CLI data frame counts against the same timer.

While pairing runs, the CLI answers at most one `commit` whose `browser_static` is not paired. A pairing `commit` whose `pair_tag` does not match the CLI's current code is ignored before this rule applies and does not use up the one answer. After that `offer`, any failure of the handshake (commit mismatch, bad MAC, all-zero key, `abort`, silence past the step's timeout, a `SessionsClosed` notice for the candidate's `sid`, words rejected on either side) ends the pairing. The user runs `jobranger pair` again. A second `commit` with an unpaired `browser_static` in the same run gets `abort` and ends the pairing. Ending the pairing aborts the candidate handshake. Commits with a paired `browser_static` get an `offer`.

## Data frames

```text
dir   = 0x01 CLI to browser, 0x02 browser to CLI
key   = key_c2b for 0x01, key_b2c for 0x02
nonce = 00 00 00 00 || u64be(seq)
aad   = LABEL || sid || dir || u64be(seq)
ciphertext field = base64url(AES-256-GCM(key, nonce, plaintext, aad))
```

The AES-256-GCM output is the encrypted bytes followed by the 16-byte tag, as Python `AESGCM.encrypt` and WebCrypto `encrypt` return it.

`seq` counts per direction, starts at 1 and the sender adds 1 per frame. `seq` stays below `2**32`. A sender whose next `seq` would reach `2**32` closes the session.

## Frame plaintext

The UTF-8 JSON of one message from `contracts/payload.schema.json`. A serialized payload over `CHUNK_THRESHOLD_BYTES` (45,056) goes as `chunk` messages, each one its own data frame.

## Commands and replies

A browser command carries an `id`, and the CLI answers it with one `saved` or `error` whose `ref` is that `id`.

Command ids are idempotency keys. The CLI keeps the `id` and the reply of every command it has answered for at least `COMMAND_DEDUPE_SECONDS` (600), and the record survives a CLI restart. A command whose `id` is in the record gets the stored reply again, and the CLI does not run it a second time. This holds across sessions: after a session ends with `unknown_session`, the browser sends its unanswered commands again on the next session with the same `id`.

## Receiver rules

A frame breaks the rules when:

- a `hello` frame has `seq` other than 0
- a `hello` step is over `HELLO_MAX_BYTES`, has an unknown or out-of-order `t`, or a binary field of the wrong size
- a `hello` step is not a JSON object, lacks a field its `t` requires, has a field its `t` does not define, has a field of the wrong JSON type, or repeats a key
- a `data` frame arrives on a `sid` that is still in its handshake
- a `data` frame has a `seq` other than the last accepted `seq` for that direction plus 1 (first frame: 1), or at or above `2**32`
- a `data` frame's `ciphertext` is longer than `CIPHERTEXT_B64_MAX_CHARS` (61,440) or decodes to fewer than `GCM_TAG_BYTES` (16) bytes
- a `data` frame's GCM tag fails

A frame that breaks the rules aborts the handshake or closes the session for that `sid`. When the relay drops a frame, the next frame breaks the `seq` rule and the receiver closes the session.

## Closing

Two unauthenticated `hello` steps close a session:

- `{"t": "abort"}`: sent by a side that aborts a handshake or closes a session.
- `{"t": "unknown_session"}`: sent by the CLI in answer to any frame other than `commit` for an unknown or closed `sid`. `abort` and `unknown_session` get no answer.

The relay delivers CLI frames to every browser on the channel, so a browser ignores frames for any `sid` it does not hold and never sends `unknown_session`.

On either step the receiver drops all state for that `sid`: keys, counters and handshake progress. The side that closes drops the same state. A browser's sessions end with its relay connection. After a reconnect it starts a new handshake.

## Hub errors

The relay reports a refusal as a SignalR error string that ends in `HubException: <reason>`. A refused `Send` fails the invocation and the connection stays open. A refused join closes the connection with that error and without reconnect. Clients read the reason after the last `HubException: ` and compare it exactly.

Refused `Send`:

| Reason | Meaning |
|---|---|
| `invalid_envelope` | The frame breaks `contracts/envelope.schema.json` or the base64url and `seq` rules above. A non-integer `v` such as `1.0` is invalid. |
| `unsupported_version` | `v` is an integer other than 1. |
| `channel_mismatch` | `channel` differs from the channel of the connection's handle. |
| `sid_in_use` | A browser sent a `sid` that another browser connection holds. The frame is not forwarded. |
| `too_many_sessions` | A browser connection already holds 32 `sid`s. The count starts again when the CLI connection closes or is replaced. |
| `rate_limited` | The connection sent more than 20 frames a second (burst 40), or its direction of the channel sent more than 256 KiB of `ciphertext` a second (burst 512 KiB). |

A valid handle admits a connection to its channel. The relay issues a CLI handle only after a key proof (`/pair/start`, `/session/cli`) and a browser handle only after a valid code or ticket (`/pair/claim`, `/session/web`). After a relay restart a CLI reconnects with a fresh handle from `/session/cli`. It asks `/pair/nonce` for that proof's nonce with its `channel`. For a channel the relay knows as paired, that request counts against the address's own limit for that channel. For any other channel it counts against the address's nonce limit. Every channel nonce also counts against its network's share (IPv4 /24, IPv6 /48). When that share is full, the relay drops the oldest outstanding channel nonce of the address that holds the most in that network, the oldest of those on a tie, and a proof that uses it gets `nonce_expired`. One address holds at most 4 outstanding nonces for a channel and 16 across all channels. Past that the relay answers HTTP 503 with `relay_full`.

Refused join:

| Reason | Meaning |
|---|---|
| `channel_full` | The channel already has 7 browser connections. |
| `ticket_full` | The browser's ticket already holds 2 connections on the channel. A ticket and every ticket refreshed from it count as one. |

A second CLI connection on a channel replaces the first. The relay sends browsers `Presence` with `cli_online: false`, calls the hub method `Replaced` (no arguments) on the old connection, closes it, and then sends `Presence` with `cli_online: true` to every connection on the channel. A browser drops its sessions on `cli_online: false` and starts a new handshake with the new CLI. A CLI that receives `Replaced` stops reconnecting.

When the CLI connection closes or is replaced, the relay frees every `sid` on the channel and sends browsers `Presence` with `cli_online: false`. Browsers drop their sessions and start new handshakes once `cli_online` is true again.

The relay closes a connection that sends nothing, pings included, for 30 seconds. When a browser connection closes, `SessionsClosed` reaches the CLI as described in [Envelope use](#envelope-use).

Before the WebSocket opens, the relay answers a missing handle, an invalid or expired handle, or a wrong `Origin` with HTTP 401 and the problem code `missing_handle`, `invalid_handle` or `wrong_origin`, and repeated failures from one address with HTTP 429. When the relay holds its maximum number of hub connections, or the client's network (IPv4 /24, IPv6 /48) holds 16, it answers HTTP 503 with the problem code `relay_full` and a `Retry-After` header of 30 seconds, and the client retries after that delay.

## Test vector

`contracts/fixtures/crypto/session-v1.json` holds one handshake and one CLI-to-browser frame from fixed inputs:

- private keys: SHA-256 of the ASCII labels `jobranger vector cli static`, `jobranger vector cli ephemeral`, `jobranger vector browser static`, `jobranger vector browser ephemeral`
- `sid`: first 16 bytes of SHA-256(`jobranger vector sid`)
- `nonce_b`: first 16 bytes of SHA-256(`jobranger vector nonce`)
- `agent`: `Firefox on macOS`
- frame: `seq` 1, plaintext `{"type":"saved","v":1,"ref":"00000000-0000-4000-8000-000000000014","applies_from":"next_run"}`, the compact JSON of `contracts/fixtures/payload/saved.json` without `recheck`
- channel: Ed25519 private key SHA-256(`jobranger vector cli ed25519`)

Expected values: public keys, `commit`, `transcript_hash`, `ikm`, `key_c2b`, `key_b2c`, `key_confirm`, `sas`, `words`, `confirm_cli`, `confirm_browser`, `frame_plaintext`, `frame_ciphertext` and `channel`.
